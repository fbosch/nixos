# Pi sandbox policy

## Scope and status

This policy describes the Linux and macOS Pi launcher generated by `modules/development/ai/pi/default.nix` and the profile in `modules/development/ai/nono/scripts/profile.json`. It does not describe the permissions of an already-running Pi process. Existing processes retain their old grants until they exit.

The persistence decision is **configuration-repo editing**. Pi setup is writable in sessions launched from the configuration repositories, and locked down in unrelated projects. The `/proc` finding remains unresolved. This is not a completed sandbox audit.

## Persistence decision: configuration-repo editing

The launcher on both platforms allows Pi setup edits when the canonical launch directory is inside `~/dotfiles` or `~/nixos`, or a registered worktree of either repository. It validates worktree metadata and the checkout backlink before matching the shared Git directory. Similar directory names, reference labels, and project settings cannot select this mode. Scope is fixed at process launch; changing directories afterward cannot upgrade an unrelated session.

In configuration-repo sessions, the default agent directory and configured `PI_CODING_AGENT_DIR` are writable. Settings, instructions, prompts, skills, and extensions can be edited with temporary-file-plus-rename operations. Stow-linked resources inside the already-authorized configuration roots remain editable. Symlinks do not authorize unrelated target directories.

**Accepted residual risk:** an agent running in these configuration sessions can plant persistent instructions, configuration, or code that future Pi sessions load. Review those changes before reloading or starting another session. This exception does not remove shell-startup, credential, reference-approval, SSH-agent, or network restrictions.

In unrelated projects, the launcher makes Pi resources read-only except for named runtime data. It protects settings, extension code, package installations, supporting libraries, and their symlink targets, even when a reference points at the dotfiles repository.

In locked-down sessions, writable agent data is limited to `sessions`, `cache`, `session-history`, `tasks`, `auth-profiles`, and `fff` directories, plus the existing `auth.json` file. The launcher prepares these data directories before confinement. It grants `auth.json` in place without making its parent writable, so credential refresh does not authorize configuration replacement. These are Pi's own credentials, not the separately denied `~/.claude/.credentials.json`.

The packaged lockfile library uses `~/.cache/pi/locks` under the launcher's `PI_LOCKFILE_DIR` setting. This lets Pi read its settings and coordinate auth updates without creating lock directories beside protected files. Jiti's writable filesystem compilation cache is disabled with `JITI_FS_CACHE=false`.

To edit Pi resources:

1. Start a fresh sandboxed Pi session from `~/dotfiles`, `~/nixos`, or a registered worktree of either repository. An existing unrelated-project session keeps its original restrictions.
2. Edit the Pi setup normally, including atomic replacement of instruction and settings files. Keep shell-startup edits on the host.
3. Review persistent changes before `/reload` or a new session. Exit conflicting sessions before changing authentication state.
4. For dependency installation, use independent copies such as Bun's `--backend=copyfile --frozen-lockfile`. Shared hard links still prevent later locked-down sessions from proving that code is protected.

Runtime data remains mutable and can be corrupted by an agent. Arbitrary project files and host-executed development scripts are separate trust boundaries. This change does not make those files trusted, prevent all denial of service, or prevent a host process from modifying Pi's resources.

## Image opening on Linux

Sandboxed image clicks use the existing desktop broker instead of launching `xdg-open` inside confinement. The agent still cannot connect directly to session D-Bus. Unsandboxed Linux sessions keep the native opener, and macOS retains its existing `open` path.

The extension converts the displayed image to PNG and sends `image.open` requests containing an upload ID, byte offset, total byte count, and base64 data. Requests accept no file path, URL, command, or environment. Fixed 32 KiB chunks stay within the existing 64 KiB IPC frame limit. The broker allows four pending uploads with at most 64 MiB reserved in total; unfinished uploads expire after 60 seconds.

The broker checks PNG signatures, chunk CRCs and ordering, raster dimensions, decompressed length, and scanline filters. It accepts non-interlaced 8-bit rasters up to 32 MiB encoded and 16 megapixels, with neither dimension above 8192. Ancillary metadata is removed before opening. The result is a static PNG representation, not the original animated file or its metadata.

Accepted files are created with mode 0600 inside the helper's private IPC directory, outside sandbox-writable temporary paths.

A per-session cache keys files by the SHA-256 of the validated, metadata-stripped PNG. Repeated clicks reuse the same file without consuming another slot. Each upload is still validated, and changed or replaced cache files are recreated. At most 24 unique files and 128 MiB are retained. Reuse refreshes a 15-minute inactivity lease; in-flight opens hold the file until launch completes. Normal broker shutdown removes the cache, and nothing is shared across sessions.

A pinned Loupe executable receives only the captured desktop connection, private runtime directories, a fixed PATH, and pinned MIME data. `XDG_DATA_DIRS` includes the packaged shared MIME database because NixOS has no usable `/usr/share/mime` default. Project environment values do not choose the viewer, its MIME database, or its session bus.

This capability permits an agent to request image windows; it does not attest that a human clicked. Resource limits bound uploads and retained files, but opening untrusted raster images still relies on the viewer's decoder security. Launch acknowledgement does not prove a window has rendered correctly.

After updating the launcher, restart Pi rather than using `/reload`. When changing the viewer environment, quit existing Loupe instances too, since a new request may reuse an existing process. Native tests verify broker delivery, private-file and D-Bus denial, cleanup, and GLib MIME detection. Actual GUI display still requires a fresh desktop-session check.

## Explicit raw launch

A leading `--no-sandbox` replaces the launcher process with raw Pi before sandbox setup. It skips policy and IPC-manifest validation, project-environment loading, sandbox resource checks, helper brokers, diagnostics injection, and credential-proxy startup. Pure agent-directory and PATH normalization still keeps the immutable launcher ahead of writable shims. Raw Pi retains its own normal configuration and authentication requirements.

Raw mode preserves the caller's environment. It does not prepare or impose the sandbox's runtime lock directory. Do not concurrently update the same auth store from raw and confined sessions unless both use the same `PI_LOCKFILE_DIR`.

The flag cannot remove kernel restrictions inherited from an already-sandboxed parent. Invoke raw mode from a host terminal when unrestricted host access is intended.

## Proxy decision: unrestricted forwarding accepted

The owner explicitly accepted unrestricted proxy forwarding for this pass. `example.com` is permitted by the default forwarding policy, not by an individual allowlist entry.

The generating profile has `network.block = false` and no `allow_domain` entries. On Linux, the standalone proxy uses that profile. Its child sandbox receives a separate profile with `network.block = true` and a grant for the proxy port. Consequently, the child's `NONO_CAP_FILE` can show `net_blocked: true` and `allowed_domains: []` while proxy forwarding remains unrestricted.

On macOS, nono manages its credential proxy within the native launch path. The launcher retains `--trust-proxy-ca` and applies the generated Seatbelt profile. Proxy implementation differs by platform; the accepted destination policy is the same.

This deliberately retains an exfiltration channel for data the agent can read. Direct TCP access to ports 22, 80, and 443 remains denied. The existing browser-port exceptions were not changed in this pass.

## Host SSH-agent access

The packaged launcher defaults `PI_NONO_SSH_AGENT=1`. When the host's `SSH_AUTH_SOCK` names an existing Unix socket, the sandbox receives connect access to that socket. Set `PI_NONO_SSH_AGENT=0` in the host launch environment to disable access. A project `.envrc` cannot enable access or select another socket.

The agent can use identities loaded into the host SSH agent for authentication and Git signing. This grants signing authority; private-key files remain denied inside the sandbox.

Interactive launches check every existing key in `pi.sandbox.ssh.agentIdentities`, which defaults to `id_ed25519` and `id_rsa`. The host launcher uses each public companion file with `ssh-add -T` to check agent usability and offers to load missing identities before confinement. These checks perform signing operations and may trigger agent confirmation prompts. Missing private-key files are skipped. Without a public companion, the launcher offers to load the key directly. Noninteractive launches do not load identities; the host must preload them.

## Azure DevOps Git over SSH

The packaged Pi launcher puts a private SSH wrapper on its PATH. Inside nono, the wrapper supplies an SSH configuration that sends `ssh.dev.azure.com:22` and `vs-ssh.visualstudio.com:22` through the existing HTTP proxy with authenticated `CONNECT`. Other hosts retain their existing transport configuration. Raw Pi sessions use native SSH without the additional configuration.

The helper connects only to the local nono proxy and rejects other destinations and ports. It does not grant direct port-22 access or read private keys. The proxy's unrestricted forwarding policy remains unchanged; the helper's Azure check is not a restriction on what an agent can otherwise request through that proxy.

Azure authentication requires its configured identity in the host agent. The default interactive preload includes `id_rsa`; noninteractive launches need that identity loaded beforehand. The sandbox receives only the existing agent socket. Existing SSH identity settings and host-key verification still apply. Accept new host keys on the host, since sandboxed `known_hosts` files are read-only.

Rebuild the launcher and start a new Pi session to receive the wrapper. `/reload` cannot change a running session's PATH or grants. `ssh-transport.test.mjs` covers CONNECT authentication, SSH byte forwarding, malformed/refused responses, destination validation, and SSH configuration selection. A real Azure push remains a deployment check.

## Claude Bridge authentication

Sandboxed Claude Bridge uses the existing Claude CLI login through a host-side capture command. No SOPS secret or additional API key is required. This is the same login, not a separately revocable credential.

The Nix-owned `credentials/claude-credential.mts` helper reads `~/.claude/.credentials.json` outside confinement and returns only `claudeAiOauth.accessToken`. It rejects unsafe permissions, symlinked or hard-linked files, malformed metadata, and tokens with at most 60 seconds remaining. It does not modify the file or return the refresh token. The proxy caches the access token for at most 30 seconds.

The `anthropic` route has the fixed upstream `https://api.anthropic.com`. The child receives a session placeholder in `CLAUDE_CODE_OAUTH_TOKEN` and the proxy's local `/anthropic` route in `ANTHROPIC_BASE_URL`. The proxy validates that placeholder and replaces its authorization header before forwarding. Raw credential environment variables are rejected; project-selected endpoint and Claude configuration-directory overrides are removed. The credential file remains denied, including in configuration-repository editing sessions.

The agent can use the authenticated Anthropic API through this route and consume the account's quota. The route protects the token from disclosure; it does not make model use unprivileged. It does not grant filesystem access to the login store or provide the refresh token to Claude Bridge.

Claude CLI retains ownership of login and refresh. If its stored access token expires, refresh the login from a host terminal with Claude CLI. Capture then picks up the updated store after its cache expires. The helper does not perform an automatic OAuth refresh or interactive login. Native macOS Keychain-only authentication is not implemented by this file-based helper and has not been tested.

Activate the rebuilt launcher and start a new Pi session to receive the new route and environment. Existing sessions do not acquire it through `/reload`. Host-launched `--no-sandbox` sessions continue to use normal Claude CLI authentication directly.

`claude-proxy.test.mjs` (in `nono-tests`, Linux) tests the real installed Claude CLI against a local synthetic Anthropic server inside a fresh Linux sandbox. The response completes with a placeholder credential, the upstream sees the captured access token, direct credential-file access and capture-helper execution inside confinement cannot recover it, incorrect placeholders are rejected, and redirects are not followed to an unrelated server. The test sends no request to Anthropic and uses no real login data. A full live Claude Bridge session after activation remains to be verified.

## Unresolved process metadata

Nono 0.80 widens its `/proc/self` read grant to `/proc` so descendants can read their own process metadata. The requested profile-only fixes did not work:

- `/proc/[0-9]*/cmdline` is rejected because deny globs support only `*` and `**`.
- `/proc/*/cmdline` and `/proc/*/comm` conflict with the self-process read grant. Nono refuses to launch because Landlock cannot subtract those denies from an allowed parent.

No ineffective deny entries were added. The proposed backend change was not approved. `/proc/1/cmdline` and `/proc/1/comm` remain readable; process isolation is still pending.

## Platform parity and validation status

Configuration-session selection, registered-worktree checks, runtime-data preparation, runtime lock locations, SSH-agent opt-in, and the leading `--no-sandbox` bypass are shared across Linux and macOS.

Linux enforces read-only controls by splitting writable ancestor grants. macOS also receives narrow agent grants, but additionally gets Seatbelt write-deny rules for protected controls, symlink targets, and ancestor replacement. This handles broad inherited macOS grants without denying reads or freezing runtime data. The launch plan carries the protected paths into profile generation, so macOS does not repeat the recursive agent scan.

The `nono-tests` check is defined for both platforms and runs every nono test file; `platform-parity.test.mjs` includes native Pi startup, settings/auth locking, runtime file writes, configuration-root/worktree edits, unrelated-project denials, and shell/credential/SSH/network regressions. FFF directory access is covered; a real macOS FFF/LMDB smoke test remains part of host validation. Platform-forced tests run the Darwin bootstrap with a recording nono stub and inspect the generated rules. They are not evidence of Seatbelt enforcement.

Native macOS validation was explicitly deferred. No SSH access, activation, or changes to the Mac were performed. Evaluating the Darwin check fully on the Linux builder also requires a Darwin build of the Pi source overlay, so it cannot complete locally. Linux native checks and Darwin bootstrap/rule-generation tests passed; macOS kernel enforcement and full interactive workflows remain unverified.

For later validation on `rvn-mac`, use the same working-tree changes, not an older clone, and run:

```sh
nix build --offline --no-link .#checks.aarch64-darwin.nono-tests
```

Then verify a fresh interactive session, FFF history, model availability, and browser/desktop integrations on the Mac before claiming functional parity. The earlier macOS Git-fsmonitor daemon limitation remains separate and unresolved.

## Verification

`agent-protection.test.mjs`, run by `nono-tests`, starts a new native nono sandbox from a Nix check. It uses synthetic credential files, a live fixture SSH-agent socket, and a Stow-style Fish configuration. It tests both the default and configured Pi directories in an unrelated-project session. The same check runs `config-editing.test.mjs` in fresh sandboxes for both configuration roots, a registered worktree, and an unrelated project. Those probes verify atomic instruction/settings/extension edits, including after changing directories, while secret, Fish startup, ungranted SSH-agent, network, and reference-approval denials remain enforced. It also starts the packaged Pi CLI in RPC mode and verifies that an extension selected by the existing settings registers its command. It does not make a model inference request.

| Finding | Before | After and verification | Result |
| --- | --- | --- | --- |
| Pi settings and extensions | Locked down in all Linux sessions. | Atomically replace instructions, settings, and extension files; create an extension directory. | Allowed from configuration repositories and their registered worktrees. Denied from unrelated projects, including after changing directories. |
| Other-process cmdline and comm | Readable through the widened `/proc` grant. | `cat /proc/1/cmdline` and `cat /proc/1/comm`. Expected denial. | Still readable. Not fixed. |
| Own cmdline | Readable. | `cat /proc/self/cmdline`. | Readable as required. |
| Proxy destinations | Unrestricted forwarding; no domain allowlist. | Inspect the generating profile and confirm owner intent. | Unchanged and explicitly accepted. No external proxy GET was repeated in this pass. |
| Direct HTTPS | Previously fixed. | Requested curl probe to `https://ifconfig.me`; separate loopback TCP probes to ports 22, 80, and 443. | Curl returns `000`. The TCP probes return `EACCES`. |
| Direct SSH | Previously fixed. | Bash opens `/dev/tcp/140.82.121.4/22`. | Denied. |
| Claude OAuth file | Previously fixed. | `cat "$HOME/.claude/.credentials.json"` against a real synthetic file. | Denied. |

| Kernel core pattern | Previously denied. | `echo p >> /proc/sys/kernel/core_pattern`. | Denied. |
| Other-process environment | Previously denied. | `cat /proc/1/environ`. | Denied. |

Nix's build network has no external DNS. Curl's `000` alone therefore does not prove the network boundary; the independent TCP probes check the kernel permission error. The fixture paths are not the workstation's live credentials or configuration. Deployment and fresh workstation verification remain separate steps.

Run the checks from the current checkout:

```sh
nix build --no-link \
  .#pi-sandbox \
  .#checks.x86_64-linux.nono-tests \
  .#checks.x86_64-linux.nono-tests-ordinary \
  .#checks.x86_64-linux.nono-typecheck \
  .#checks.x86_64-linux.nono-pi-nix-build-access
```

`nono-tests` runs every file in `modules/development/ai/nono/__tests__` against the restricted profile the launcher ships; tests skip themselves when the tool they need is not provided. `nono-tests-ordinary` repeats the profile-dependent GitHub, Azure and socket-isolation tests with the ordinary profile. `nono-pi-nix-build-access` is the NixOS VM test for sandboxed Nix builds.

A passing build covers the implemented protections. It does not close the explicitly unresolved `/proc` finding.
